### 1. Meeting Overview
The team briefly discussed their current pull request (PR) review approach and how approvals should work going forward. The focus was on balancing code quality with development flow and avoiding bottlenecks caused by specific reviewers.
Matheus explained his previous experience where a single approval is enough to merge, and developers may optionally request a specific reviewer (e.g., someone with deeper knowledge of that area) when they feel changes are risky or touch sensitive parts of the code.
He highlighted that having a single “code owner” who must review every PR can significantly slow progress and should be avoided.
The group aligned that the current rule stands: if one person approves the PR, it can be merged, while developers remain responsible for the impact of their own changes.
Arno reiterated that reviewers will do their best to understand changes but will not deeply learn every part of each other’s code; if something breaks later, the original author should return to fix it.
​
---
### 2. Technical Discussions
The team discussed options for safely testing changes in CI/CD pipelines (Jenkins and GitHub Actions) without impacting the main branch.
Anuj described how in Jenkins it is possible to run a pipeline against a specific user’s repository or branch so only that user’s code is deployed, leaving main untouched and allowing easy rollback to the stable main deployment.
He noted he would investigate whether a similar pattern is possible with GitHub Actions for this project.
Arno confirmed that pipelines can be structured with different stages/environments and that deploying from specific branches is supported.
​Ronan added that GitHub Actions workflows can be configured to run only on particular branches or even specific folders, enabling partial or scoped deployments for testing before touching the full environment.
​
---
### 3. Project Processes
The discussion refined how code review responsibility and deployments fit into the team’s working agreements.
The PR policy was reaffirmed: one approval is sufficient to merge, and developers may tag particular teammates (e.g., domain experts) when they feel changes are complex or high-risk.​
The team agreed to avoid making any single person a mandatory reviewer for all PRs to reduce blocking and maintain flow.​
There was a shared understanding that experimenting with branch- or folder-based deployments in GitHub Actions can support safer testing without changing the agreed review workflow.​

---
### 4. Next Steps
The group decided to keep further exploration of deployment improvements as follow-up work and move on to the scheduled roundtable.​
Anuj will check how to replicate his Jenkins “user repo/branch” deployment strategy in GitHub Actions for this project.
The team will consider adding workflows that deploy from specific branches or folders to a test environment, supporting individual 
testing when developers are unsure about potential breakage. The meeting then transitioned into the planned roundtable segment and formal 
recording start.
